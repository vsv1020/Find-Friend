## 1. 总策略:把 V1 再切成三刀

PRD §6 已经说对了核心原则——**「让人来参加一个活动,而不是来试用一个 App」**。
把这句话推到底,会得到一个比 PRD §4.1 更激进的结论:**前 5 场活动根本不需要「发局」「审核后台」和「群聊」**,因为局主只有 Victor 一个人,他不需要给自己审核,也可以手动拉微信群。

因此建议把 V1 拆成三个可独立上线的版本,每一版都能拿到真实数据:

| 版本 | 工期 | 交付什么 | 验证什么 | 对应 PRD 冷启动阶段 |
|---|---|---|---|---|
| **V0.5 一页纸报名** | **第 1 周** | 可分享的局详情页 + 手机号报名 + 后台手动录局 + 短信通知 | **链接打开 → 完成报名转化率 > 25%**(PRD §8 辅助指标之一)。这是整个产品最先该被验证的数字 | 第一阶段前半 |
| **V1.0 自助发局闭环** | **第 2 到 4 周** | 用户体系、发局表单、审核队列、自动成团判定、通知体系、局内群聊、靠谱度评价 | **非官方局能否成团**(真北极星) | 第一阶段后半 → 第二阶段 |
| **V1.5 运营与增长工具** | **第 5 到 6 周** | 数据看板、报名成功页推荐位、局主工具、白名单 POI 管理、举报与封禁 | **每周稳定 10 场以上、二次参加率 > 35%** | 第二阶段 |

> **为什么这么切:** 如果 V0.5 的报名转化率只有 8%,那么 V1.0 的发局、审核、群聊全都白做——问题出在活动本身没吸引力,而不是功能不够。**用 1 周换掉 3 周的风险,是这个项目最划算的一笔交易。**

## 3. 数据模型(建议直接采用)

这套表结构是把 PRD §5「防滑向约会」的结构设计**硬编码进数据库**的结果——不是靠前端不显示,而是让「按人检索」在数据层就做不到。

```sql
-- M1 身份:手机号为唯一主键(见评审 §3-7)
users (
  id            uuid pk,
  phone         text unique not null,      -- 唯一身份锚点
  wx_openid     text unique,               -- 预留,V1.5 小程序接入时才写
  nickname      text not null,
  gender        text check (in ('male','female','other')),  -- 首次报名时补齐
  avatar_url    text,
  reliability   int  default 100,          -- 靠谱度分,爽约扣分
  no_show_count int  default 0,
  status        text default 'active',     -- active / restricted / banned
  created_at    timestamptz
)

-- M2 白名单场地(见评审 §3-8,局主只能选不能自由输入)
venues (
  id, name_zh, name_en, scene_type, address,
  lat, lng, gmap_place_id, avg_price_thb,
  is_active bool default true
)

-- M2 局:产品的核心对象
events (
  id            uuid pk,
  host_id       uuid -> users,
  scene_type    text check (in ('coffee','art','bar')),
  venue_id      uuid -> venues,
  start_at      timestamptz not null,
  duration_min  int default 120,
  capacity_min  int not null,   -- 系统按场景固定:coffee=2 / art=3 / bar=4
  capacity_max  int not null,   -- 局主可改,默认 coffee=4 / art=6 / bar=8
  price_est_thb int,
  description   text,           -- 一句话说明
  status        text not null,  -- 见 §4 状态机
  is_official   bool default false,  -- Victor 发起 → true,用于指标去噪(见评审 §4.4)
  share_slug    text unique,    -- 短链,分享卡片用
  reviewed_by   uuid, reviewed_at timestamptz, review_note text,
  formed_at     timestamptz, chat_archived_at timestamptz,
  created_at    timestamptz
)

-- M3 报名
signups (
  id, event_id -> events, user_id -> users,
  status text,  -- applied / waitlist / confirmed / cancelled / attended / no_show
  created_at, cancelled_at,
  unique (event_id, user_id)
)

-- M6 群聊(活动结束 48h 后按 chat_archived_at 变只读)
messages ( id, event_id, user_id, content, created_at )

-- 靠谱度评价:只评行为,不评人(PRD §5 结构层第四条)
reliability_marks (
  id, event_id, rater_id, ratee_id,
  mark text check (in ('on_time','late','no_show')),   -- 仅此三个枚举,不可扩展
  created_at
)

-- M5 通知
notifications ( id, user_id, event_id, channel, template_key, payload jsonb,
                status, sent_at, error )

-- M8 埋点(未登录也要能记,用 anon_id)
analytics_events ( id, anon_id, user_id, name, props jsonb, created_at )
```

**三条必须写进 Row Level Security 的约束(这是产品护城河,不是技术细节):**
1. `users` 表**永远不对其他用户开放列表查询**——不存在「浏览用户」的接口,从根上杜绝「翻头像」。
2. `signups` 对非同局用户不可见;局详情页只返回**计数**(已报 n / 还差 m),不返回参与者身份(见评审 §4.2)。
3. `messages` 仅同一 `event_id` 且 `status='confirmed'` 的报名者可读写;`chat_archived_at` 过后转只读。

## 4. 局(Event)状态机 —— 开发前必须对齐的唯一一张图

```
  draft ──提交──> pending_review ──审核拒绝──> rejected
                        │
                     审核通过
                        ↓
                      open  ←── 报名/取消在此状态下发生
                        │
              (start_at - 12h 定时判定)
                        │
        ┌───────────────┴────────────────┐
   报名数 >= capacity_min          报名数 < capacity_min
        ↓                                ↓
     formed ──> 发成团短信            cancelled_low ──> 发解散短信
        │                                    (并推荐同时段其他局)
   (start_at + duration)
        ↓
      done ──> 局主标记到场/爽约,参与者互评靠谱度
        │
   (done + 48h)
        ↓
    archived ──> 群聊转只读
```

**关键规则(对应评审 §3):**
- `open → formed/cancelled_low` 的判定时点固定为 **start_at − 12 小时**(定时任务)。
- `formed` 后**锁定**:不再接受新报名;此时取消记 1 次爽约。
- 审核 SLA 2 小时;超 6 小时未审自动转 `open` 并打标待复核。
- 性别配比在 `signups.count >= 4` 时才生效,且只把超配性别的新报名转 `waitlist`,**不直接拒绝**。

## 7. 埋点清单(对齐 PRD §8 四个指标)

| 指标 | 计算式 | 依赖埋点/字段 |
|---|---|---|
| **成团率(北极星)** | `count(status in ('formed','done','archived')) / count(审核通过并公开过的局)` | `events.status`,按 `is_official` 分组 |
| **非官方局成团率(真北极星)** | 同上,`is_official = false` 且 Victor 未补位 | `events.is_official` + 补位标记 |
| 链接→报名转化率 | `signup_success / page_view(event_detail)` | `analytics_events`,**未登录需用 anon_id 记录** |
| 30 天二次参加率 | 首次 `attended` 后 30 天内再次 `attended` 的用户占比 | `signups.status='attended'` |
| 非 Victor 发起的局占比 | `count(is_official=false) / count(all)` | `events.is_official` |

> ⚠️ 转化率指标要求**未登录状态就开始记录**。这会影响首屏结构(anon_id 需在服务端首次响应时下发 cookie),必须在 T04 开发时一并做掉,事后补埋点等于重跑一遍冷启动。
