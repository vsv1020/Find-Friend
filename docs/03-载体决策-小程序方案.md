## 3. 上线链路与排期解耦

```
已有企业执照 → 注册小程序 → 微信认证(1-3 工作日, 300 元/年)
             → ICP 备案(约 1-3 周,各省管局差异大)
             → 类目申报 → 首次代码提审(1-7 天)
```

### 🔍 需立刻确认:体验版是否也需备案

微信对未备案小程序的限制近年持续收紧,当前规则下**体验版是否受限需在小程序后台实测确认**。这决定第一场活动的组织方式:

| 情况 | 第 1-4 周怎么办 |
|---|---|
| **体验版不受限** | 按原计划:体验版办真实活动拿数据,与备案并行。体验版可加 100 名成员,恰好覆盖 PRD §5「早期一百个用户定义社区气质」的规模 |
| **体验版也需备案** | **备案今天启动**;前 2-3 场退回**微信群接龙手工报名**,照常验证活动本身的吸引力,不影响开发排期 |

> 两种情况下开发都不被阻塞。差别只在于「小程序什么时候能用上」。

**迭代节奏:** 正式版发布放缓到每周一次,日常验证全部走体验版/开发版。

## 4. 身份体系:openid + phone 双层(重要,与直觉相反)

企业主体拿回了 `getPhoneNumber`,但**不能据此把手机号当作通知通道**:

> ⚠️ `getPhoneNumber` 返回的是**用户微信绑定的手机号**。目标用户是在曼谷的华人,微信绑定的大概率是 **+86 号码**,而非他们在泰国日常使用的泰国号。该国内号可能已停用或未随身携带。
> **拿到的号 ≠ 用户在泰国能收到短信的号。**

### 方案

| 字段 | 来源 | 用途 | 何时采集 |
|---|---|---|---|
| `openid` | 小程序自动注入 | **登录态**,零成本鉴权 | 首次进入 |
| `phone` | `wx.getPhoneNumber` | **账号唯一性锚点** —— 防止换微信号洗掉爽约记录 | 首次报名时 |
| `notify_phone` | 用户手填(可选) | 泰国本地号,短信兜底通知 | 成团页引导填写,非必填 |

### 通知通道优先级
1. **订阅消息(主通道)** —— 用掉一次就在下一个触点补授权,见 §9
2. **站内消息** —— 用户回访时可见
3. **短信(兜底,可选)** —— 仅当用户填了 `notify_phone`;成团/解散两条关键通知

### 报名流(V0.5)
```
点报名 → getPhoneNumber 授权 → 填昵称 + 性别 → 授权订阅消息 → 完成
```
四步,但其中两步是一键授权弹窗,实际耗时约 15 秒。**仍显著优于 H5 的短信验证码流程。**

> **对 `02` 文档的影响:** `users` 表主键 `phone` → `openid`;`phone` 保留为唯一索引;新增 `notify_phone` 可空字段。

## 5. 技术选型

### 5.1 Supabase 出局
1. 小程序 `wx.request` 域名白名单要求**已备案域名**,Supabase 域名无法备案;
2. 境外服务器,国内备案体系下的合规路径不清晰;
3. 云开发可省掉大量鉴权与域名配置工作。

### 5.2 后端:微信云开发 CloudBase

| 优势 | 说明 |
|---|---|
| 不阻塞开发 | `wx.cloud` 调用不走域名白名单,备案排队期间即可全量联调 |
| 鉴权零成本 | openid 自动注入,与 §4 的身份方案天然契合 |
| 实时能力 | 数据库 watch 可支撑 V1.0 的群聊 |
| 定时任务 | 云函数定时触发器,直接支撑成团判定(`02` §4 状态机) |

**代价:** 文档型数据库,`02` §3 的关系模型需改写(约 +0.5 人天)。
**改写要点:** 外键手动维护 + 适度冗余(`events` 内冗余 `signup_count`、`gender_counts`);`02` §3 的三条 RLS 约束改用**云函数统一出口 + 数据库安全规则**实现——**产品护城河不变:依然禁止任何按人检索的接口。**

### 5.3 跨境延迟
服务器在国内、用户在曼谷,RTT 约 **100–200ms**。本产品为低频交互(浏览、报名、查看通知),**该延迟可接受,不构成 blocker**。若后续实测体验不佳,可评估云开发的境外环境或 CDN 加速。

### 5.4 其余替换

| 原选型 | 替换为 |
|---|---|
| Google Maps | 腾讯位置服务(`wx.chooseLocation` + `map` 组件) |
| Next.js + H5 | 小程序原生(V1 单端,无需 Taro) |
| Supabase Auth | openid + `getPhoneNumber`(见 §4) |
| PromptPay(V2) | **微信支付**(企业主体已解锁) |

> ⚠️ **腾讯位置服务对曼谷的 POI 覆盖质量需实测。** 若覆盖不佳,`02` T03 的「白名单 POI 库」方案更可靠——Victor 手工录入 30 家场地的名称与坐标,不依赖任何地图服务商。**建议无论如何都以白名单为准**,它同时解决了假地址与审核成本问题。

## 6. 小程序载体的固有代价

### 6.1 🔴 无法直接分享到朋友圈 —— 改变冷启动物料形态

PRD §6 原方案为「每场生成一个可分享链接,**直接扔进朋友圈和现有微信群**」。小程序只能分享给好友/群,**朋友圈无法发送小程序卡片**。

**应对(必须进 V0.5):**
> 「生成分享链接」改为「**自动生成分享海报**」——活动主视觉 + 场景/时间/地点 + 「还差 N 人」 + 小程序码,局主一键保存到相册后发朋友圈。
> 技术:云函数 canvas 绘制 + `wxacode.getUnlimited` 生成带场次参数的小程序码,扫码直达该场局详情页。

### 6.2 每次改代码要提审
见 §3 的缓解方案。

## 7. 类目申报策略

**核心原则:不报「社交」类目。** 即使企业主体可选社交类目,报「社交-婚恋交友」会把产品钉死在交友定位上——**与 PRD §5 的全部设计背道而驰**,且带来更严的资质与内容监管。

**论证武器是 PRD §5 本身** —— 「只匹配活动不匹配人」「不开放陌生人私聊」「无用户检索接口」「评价只评靠谱度」。据此正当论证:**本产品是活动组织与报名工具,不是陌生人社交产品。** 建议申报「生活服务」/「文娱-活动」方向。

| 触发点 | 缓解 |
|---|---|
| 群聊功能 | 命名为「**行前沟通**」而非群聊;仅成团后开放;UI 常驻「活动结束 48 小时后关闭」;**不提供加好友入口** |
| UGC 内容 | **强制接入** `security.msgSecCheck`(发局文案、群聊消息、昵称)与 `mediaCheckAsync`(头像、图片);命中进人工复核队列 |
| 未成年人 | 用户协议明确限 18 岁以上;酒馆局额外提示 |

> 微信类目规则会调整,注册后应在小程序后台类目页核对当下实际要求。

## 8. 合规(企业主体 + 国内服务器 + 泰国用户)

**这是一个跨境数据场景,两套法域同时适用:**

| 法域 | 适用原因 | 必做动作 |
|---|---|---|
| **泰国 PDPA** | 用户是在泰国的自然人 | 隐私政策须**明确写出数据存储地在中国大陆**并取得告知同意;提供访问/删除/撤回同意的入口 |
| **中国 PIPL 等** | 主体与服务器在国内 | 个人信息收集清单、**小程序后台「用户隐私保护指引」**、账号注销入口 |
| 通用 | 线下活动 | 用户协议明确**线下活动人身安全责任边界与免责**;一键举报入口 |

> ⚠️ 数据存储地告知是 PDPA 的**必填项,不是 nice-to-have**。建议找泰国本地法务过一遍 T30 产出的文件。

## 9. 通知方案

订阅消息为「一次授权一次推送」,长期订阅仅对公共服务类目开放。**标准解法:用掉一次,就在下一个触点补一次。**

```
报名成功页 → 引导授权①  ──成团时用掉①──▶ 成团结果页 → 引导授权②  ──开场前3h提醒用掉②
                        └─未成团→解散通知页补授权,同时推荐同时段其他局
```

短信兜底见 §4:仅对填写了 `notify_phone`(泰国号)的用户生效,覆盖成团/解散两条。
