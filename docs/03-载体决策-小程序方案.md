## 2. 小程序的三个真实收益(要用足)

1. **`wx.getPhoneNumber` 一键授权手机号** —— 最大收益。报名流从「输号码 → 等短信 → 填验证码 → 补资料」压缩为「点报名 → 授权 → 完成」两步。H5 无此能力。这直接服务于 PRD §8 的「链接打开→完成报名转化率 > 25%」目标。
   - 前提:**企业主体 + 微信认证**,个人主体无此接口。
2. **无域名拦截风险** —— H5 在微信内被拦截显示「已停止访问」的隐患消失。
3. **分享到群的卡片体验更好**,不会被折叠成普通链接。

---

## 3. 小程序的三个代价(必须提前设计)

### 3.1 🔴 小程序不能直接分享到朋友圈 —— 改变冷启动物料形态

PRD §6 的原方案是「每场生成一个可分享链接,**直接扔进朋友圈和现有微信群**」。小程序只能分享给好友/群,**朋友圈无法发送小程序卡片**。

**应对(必须进 V0.5,不可推后):**
> 把「生成分享链接」改为「**自动生成分享海报**」——活动主视觉 + 场景/时间/地点 + 「还差 N 人」 + 小程序码,局主一键保存到相册后发朋友圈。
> 技术:云函数用 canvas 绘制 + `wxacode.getUnlimited` 生成带场次参数的小程序码,扫码/长按直达该场局详情页。

### 3.2 上线链路变长(外部依赖,不可压缩)

```
营业执照 → 注册小程序 → 微信认证(1-3 工作日, 300 元/年)
        → ICP 备案(约 1-3 周,各省管局差异大)
        → 类目申报 → 首次代码提审(1-7 天,社交相关可能多次打回)
```

**行动:该链路今天启动,与开发并行。** 备案是整个排期上最长的杠杆。

### 3.3 迭代要提审

**缓解:前 4 周全程跑「体验版」。** 体验版无需提审,可直接加最多 100 个体验成员——恰好覆盖 PRD §5 运营层「早期一百个用户定义社区气质」的规模。
**这意味着:备案没下来也能先办活动、先拿数据。** 这是本次载体变更后最重要的排期结论。

## 4. 类目申报策略(决定能否上线)

**核心原则:不报「社交」类目。** 社交-婚恋交友、社交-社区论坛会触发额外资质要求,小微主体难以满足。

**论证武器就是 PRD §5 本身** —— 「只匹配活动不匹配人」「不开放陌生人私聊」「无用户检索接口」。据此可以正当地论证:**本产品是活动组织与报名工具,不是陌生人社交产品。** 建议申报「生活服务」/「文娱-活动」方向,参照活动行、互动吧一类产品的定位。

**两个审核触发点及缓解:**

| 触发点 | 风险 | 缓解 |
|---|---|---|
| 群聊功能 | 易被判定为社交 | 命名为「**行前沟通**」而非群聊;仅成团后开放;UI 常驻「活动结束 48 小时后关闭」;不提供加好友入口 |
| UGC 内容 | 不接内容安全会被直接打回 | **强制接入** `security.msgSecCheck`(发局文案/群聊消息/昵称)与 `mediaCheckAsync`(头像/图片),新增为 V0.5 任务 |

> 微信类目规则会调整。注册后应在小程序后台类目页核对当下实际要求,本节给的是策略方向而非清单。

## 5. 技术选型全量替换

### 5.1 Supabase 出局(三个原因,任一即足够)
1. 境外服务器,国内访问延迟与稳定性不可控;
2. 小程序 `wx.request` 域名白名单要求**已备案域名**,Supabase 域名无法备案;
3. 中国大陆用户个人信息出境,在《个人信息保护法》下需单独合规路径(标准合同/安全评估)。

### 5.2 替代方案

| | **方案 A:微信云开发 CloudBase(V1 推荐)** | 方案 B:腾讯云/阿里云 + Node + PostgreSQL |
|---|---|---|
| 是否阻塞开发 | **不阻塞**(`wx.cloud` 调用不走域名白名单) | 需备案域名才能联调 |
| 鉴权 | openid 自动注入,零成本 | 自行实现 |
| 群聊实时 | 数据库 watch | 自建 WebSocket |
| 成团定时判定 | 云函数定时触发器 | cron |
| 数据模型 | **文档型,需改写 `02` 文档的关系模型** | 关系型,可直接复用 |
| 后续多端 | 迁移成本高 | 天然支持 |

**结论:V1 用 A。** 唯一且充分的理由是「不阻塞开发」——备案排队期间即可跑体验版办活动。代价是数据模型改写(约 0.5 人天)。

**改写要点:** 外键关系改为手动维护 + 适度冗余(如 `events` 内冗余 `signup_count`、`gender_counts`);`02` 文档 §3 的三条 RLS 约束改用**云函数统一出口 + 数据库安全规则**实现,产品护城河不变——**依然禁止任何按人检索的接口**。

### 5.3 其余替换

| 原选型 | 替换为 |
|---|---|
| Google Maps | 腾讯位置服务(`wx.chooseLocation` + `map` 组件) |
| PromptPay(V2) | 微信支付(V2,需企业主体) |
| Next.js + H5 | 小程序原生 / Taro(若未来仍要多端则选 Taro) |
| Supabase Auth(手机 OTP) | `wx.getPhoneNumber` 一键授权,手机号仍为唯一主键 |

## 6. 通知方案(订阅消息的正确打法)

订阅消息为「一次授权一次推送」,长期订阅仅对公共服务类目开放,活动类无法获得。**标准解法:用掉一次,就在下一个触点补一次。**

```
报名成功页 → 引导授权 ①  ──成团时用掉①──▶  成团结果页 → 引导授权 ②  ──开场前3h提醒用掉②
                                                 (未成团则在解散通知页补授权,用于推荐其他局)
```

**短信兜底最关键的两条:成团、解散。** 国内短信约 ¥0.03–0.05/条,100 人/月成本可忽略。
若后续开通服务号,可增加模板消息作为第三通道。

**新增:**
| # | 任务 | 说明 | 估时 |
|---|---|---|---|

> **第 1 到 4 周走体验版办真实活动拿数据,与备案并行;备案与类目通过后再发布正式版。**

## 9. 阻塞中的三项决策(需 Victor 拍板)

| # | 决策 | 为什么阻塞 |
|---|---|---|
| **1** | **首发城市** | 密度风险是 PRD §9 的第一风险。国内必须单城市甚至单商圈切入,这决定 POI 白名单、场景清单(替代曼谷咖啡馆/BACC)、种子用户来源。**PRD §3 的三个场景需要按该城市重写。** |
| **2** | **谁当第一个局主** | PRD §6 冷启动完全依赖「Victor 本人亲自办 5-8 场」。若 Victor 人在曼谷而市场在国内,这条路径断裂,需要替代方案(本地合伙人 / 与现有社群主理人合作 / 远程组织 + 本地志愿局主)。**这是当前最大的未解风险。** |
| **3** | **主体类型** | 个人主体无法使用 `wx.getPhoneNumber`、无法接微信支付、类目受限——**等于放弃小程序的最大收益**。建议企业主体或个体工商户。是否已有可用主体,决定 T29 起点。 |
