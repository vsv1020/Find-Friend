## 2. 🔴 核心约束:个人主体做不了「平台型」小程序

微信对**个人主体小程序**的定位是个人开发者的**工具/展示类**应用,而非「让用户互相发布信息」的平台服务。

**这直接冲突的是 PRD §4.1 的两项功能:**

| PRD §4.1 功能 | 个人主体下 | 结论 |
|---|---|---|
| **发局**(用户自助发布活动) | ❌ 属于信息发布平台形态,过审风险极高 | **阻塞,须升级主体** |
| **临时群聊** | ❌ 易被判定为社交类目 | **阻塞,须升级主体** |
| 报名、成团通知、人工审核后台 | ✅ 可做 | 不阻塞 |

**个人主体额外失去的能力:**
- ❌ `wx.getPhoneNumber` 一键授权手机号 —— 载体决策 v1 中「小程序最大收益」不再成立
- ❌ 微信支付 —— V1 不收保证金(见 `01` §3-10),暂不影响
- ⚠️ 可选类目范围受限 —— 具体清单以小程序后台实际显示为准

## 3. ✅ 解法:V0.5 的形态恰好是个人主体能做的

`02-任务拆解与落地方案.md` 提出的 **V0.5「一页纸报名」**——**只有 Victor 一人办局,其他人只浏览与报名**——天然规避了上述全部冲突:

| 审核风险点 | V0.5 的状态 |
|---|---|
| 用户自助发布信息 | **无**(仅管理员后台录局)→ 定位为「活动报名工具」,非平台 |
| UGC 内容 | **几乎为零**(仅昵称)→ 内容安全压力极低 |
| 群聊/社交 | **不做**(前几场手动拉微信群,本来 V0.5 就不该做) |
| 支付 | **不做** |

> **结论:个人主体不阻塞 V0.5,只阻塞 V1.0 的自助发局与群聊。**
> 可以一边用 V0.5 跑前 5 到 8 场真实活动,一边并行解决主体升级。这与 `02` 文档的三阶段切分完全兼容。

## 4. 身份体系改为 openid 为主键(个人主体下的更优解)

拿不到 `getPhoneNumber` 后,与其退回短信 OTP(泰国手机号发短信成本高、通道复杂),不如 **V0.5 完全不要手机号**:

| | 原方案(手机号为主键) | **新方案(openid 为主键)** |
|---|---|---|
| 报名流 | 输号码 → 等短信 → 填验证码 → 补资料 | **点报名 → 填昵称+性别 → 完成** |
| 步骤数 | 4 步 | **2 步** |
| 通知依赖 | 短信 | **订阅消息**(不需要手机号) |
| 鉴权成本 | 需接短信服务商 | openid 由小程序自动注入,零成本 |

**代价:** 换微信号即为新账号,爽约记录可绕过。
**为什么可接受:** V0.5 只有数十人规模且 Victor 本人到场,防爽约靠人不靠系统。手机号推迟到 V1.0 真正需要时再补(届时主体已升级,可直接用 `getPhoneNumber`)。

> 这一改反而更贴合 PRD §4.1 的「**先看内容再要身份**」原则。
> **对 `02` 文档的影响:** `users` 表主键由 `phone` 改为 `openid`,`phone` 变为 V1.0 补充的可空字段。

## 5. 主体升级路径(V1.0 之前必须选定)

| 路径 | 说明 | 评价 |
|---|---|---|
| **A. 泰国公司 → 海外主体小程序** | 人与业务均在曼谷,注册泰国公司是自然动作。**海外主体小程序无需 ICP 备案**,服务器可置于境外,对曼谷用户延迟更优 | **最匹配实际情况**。海外主体小程序的具体能力限制需在微信开放平台核实 |
| **B. 国内个体工商户 / 公司** | 流程成熟、类目空间大、可接微信支付。需 ICP 备案,服务器在国内 | 稳妥,但与「用户在曼谷」略有错配 |
| **C. 维持个人主体** | 永远停留在「Victor 的活动报名工具」,无法开放自助发局 | ❌ **等于放弃 PRD §6 第三阶段(陌生用户主动开局并成团),产品跑不通** |

**待确认(阻塞 V0.5 启动):** Victor 是否持有中国大陆身份证——个人主体小程序注册与 ICP 备案均需要。若无,V0.5 需直接走路径 A。

**关于跨境延迟:** 若走路径 B,曼谷访问国内服务器约 100–200ms RTT。本产品为低频交互(浏览、报名、查看通知),**该延迟可接受,不构成 blocker**。

## 6. 小程序载体的三个代价(与主体无关,始终存在)

### 6.1 🔴 小程序无法直接分享到朋友圈 —— 改变冷启动物料形态

PRD §6 原方案为「每场生成一个可分享链接,**直接扔进朋友圈和现有微信群**」。小程序只能分享给好友/群,**朋友圈无法发送小程序卡片**。

**应对(必须进 V0.5):**
> 将「生成分享链接」改为「**自动生成分享海报**」——活动主视觉 + 场景/时间/地点 + 「还差 N 人」 + 小程序码,局主一键保存到相册后发朋友圈。
> 技术:云函数 canvas 绘制 + `wxacode.getUnlimited` 生成带场次参数的小程序码,扫码直达该场局详情页。

### 6.2 上线链路变长

```
小程序注册 → (个人主体无需微信认证) → ICP 备案(约 1-3 周,走海外主体则免)
          → 类目申报 → 首次代码提审(1-7 天)
```
**缓解 —— 这是本次决策最重要的排期结论:**
> **前 4 周全程跑「体验版」。** 体验版无需提审,可加最多 100 名体验成员——恰好覆盖 PRD §5 运营层「早期一百个用户定义社区气质」的规模。
> **即:备案与审核尚未完成时,已可办真实活动、拿真实数据。**

### 6.3 迭代要提审
正式版发布节奏放缓到每周一次;日常开发验证全部走体验版。

## 7. 类目申报策略

**核心原则:不报「社交」类目。**

**论证武器是 PRD §5 本身** —— 「只匹配活动不匹配人」「不开放陌生人私聊」「无用户检索接口」。据此可正当论证:**本产品是活动组织与报名工具,不是陌生人社交产品。**
V0.5 阶段这个论证尤其成立,因为**用户连发布内容的能力都没有**。

| 触发点 | V0.5 | V1.0(主体升级后) |
|---|---|---|
| 用户发布内容 | 无 | 需接 `security.msgSecCheck` 检发局文案 |
| 群聊 | 不做 | 命名为「**行前沟通**」;仅成团后开放;常驻「活动结束 48 小时后关闭」;无加好友入口;接内容安全 |
| 昵称/头像 | 建议接 `msgSecCheck` / `mediaCheckAsync` | 同左 |

> 微信类目规则会调整,注册后应在小程序后台类目页核对当下实际要求。

## 8. 技术选型替换

### 8.1 Supabase 出局
1. 小程序 `wx.request` 域名白名单要求**已备案域名**(走国内主体时),Supabase 域名无法备案;
2. 若走路径 B,中国大陆备案体系下的服务需境内部署;
3. 云开发方案可省掉大量鉴权与域名配置工作。

### 8.2 后端方案

| | **方案 A:微信云开发 CloudBase(V0.5 推荐)** | 方案 B:自建(腾讯云/阿里云 或 境外) |
|---|---|---|
| 是否阻塞开发 | **不阻塞**(`wx.cloud` 调用不走域名白名单) | 需备案域名才能联调 |
| 鉴权 | **openid 自动注入** —— 与 §4 的身份方案天然契合 | 自行实现 |
| 群聊实时(V1.0) | 数据库 watch | 自建 WebSocket |
| 成团定时判定 | 云函数定时触发器 | cron |
| 数据模型 | 文档型,需改写 `02` §3 的关系模型 | 关系型,可直接复用 |
| 海外主体适配 | 需确认海外主体小程序对云开发的支持 | 灵活,可部署新加坡(离曼谷最近) |

**结论:V0.5 用方案 A**(不阻塞开发 + openid 鉴权零成本)。若主体最终走路径 A(泰国公司),V1.0 时评估迁往方案 B 部署新加坡节点。

**数据模型改写要点:** 外键改为手动维护 + 适度冗余(`events` 内冗余 `signup_count`、`gender_counts`);`02` §3 的三条 RLS 约束改用**云函数统一出口 + 数据库安全规则**实现——**产品护城河不变:依然禁止任何按人检索的接口。**

### 8.3 其余替换

| 原选型 | 替换为 |
|---|---|
| Google Maps | 腾讯位置服务(`wx.chooseLocation` + `map` 组件);**曼谷 POI 覆盖需实测**,不足则退回白名单 POI 手工录入坐标 |
| Next.js + H5 | 小程序原生(V1 单端,无需 Taro) |
| Supabase Auth 手机 OTP | **openid 直接作为身份**(见 §4) |
| PromptPay(V2) | 微信支付(V2,需主体升级) |

> ⚠️ **腾讯位置服务对曼谷的 POI 数据质量需要实测。** 若覆盖不佳,`02` 文档 T03 的「白名单 POI 库」方案反而更可靠——Victor 手工录入 30 家场地的名称与坐标即可,不依赖任何地图服务商的 POI 库。

## 9. 通知方案

订阅消息为「一次授权一次推送」,长期订阅仅对公共服务类目开放。**标准解法:用掉一次,就在下一个触点补一次。**

```
报名成功页 → 引导授权①  ──成团时用掉①──▶ 成团结果页 → 引导授权②  ──开场前3h提醒用掉②
                        └─未成团→解散通知页补授权,同时推荐其他局
```

**V0.5 不接短信**(无手机号、泰国短信通道成本与复杂度高)。
**V1.0 补手机号后**,再将短信作为「成团/解散」两条关键通知的兜底。
