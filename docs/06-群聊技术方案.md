# 群聊技术方案(T17)

> 状态:**✅ 已实现**(`cloudfunctions/chat` + `miniprogram/pages/chat` + `common/chat.js`)。
> 结论:**V1 用轮询,不用 watch。** 理由不是省事,是有一个真实的架构矛盾。

---

## 1. 产品定位决定技术选型

PRD §4.1 叫它「临时群聊」,但按 §5 的设计,它其实是**行前沟通工具**,不是社交场:

- 只在成团后开放,活动结束 48 小时后归档转只读;
- 一个局最多 8 到 10 人(D03 的人数硬顶);
- 实际内容是「我到了」「晚十分钟」「在二楼靠窗」;
- **不提供加好友入口** —— 想继续联系的人自行交换联系方式。

`03` §7 还提到:类目申报时它应命名为「行前沟通」而非「群聊」。技术方案也该匹配这个定位。

---

## 2. 两条路

### 方案 A:`db.watch()` 实时推送

云开发原生能力,本质是客户端与数据库之间的 WebSocket 长连接。

**⚠️ 核心矛盾:`watch` 是客户端直连数据库的,走数据库权限,不走云函数。**

而 `05` §1 定的是「所有集合权限设为仅管理端可读写,前端一律走云函数」—— 这条恰恰让 watch 用不了。
集合级权限只有「所有用户可读」「仅创建者可读写」这几档,**没有「仅同一个局的成员可读」这一档**。开了「所有用户可读」就等于任何人能监听任何局的聊天,直接违背 §5 的隔离设计。

**绕开的办法:自定义安全规则**(支持 `get()` 跨文档引用):

```json
{
  "read":  "get(`database.eventMembers.${doc.eventId}_${auth.openid}`) != null",
  "write": false
}
```

需要配套:
- 新增 `eventMembers` 集合,文档 `_id = ${eventId}_${openid}`,成团时由云函数写入,作为 watch 的授权凭据;
- 写消息仍走云函数(要过 `msgSecCheck` 内容安全 + 校验归档状态),所以 `write: false`;
- 归档后读权限保留(历史可见),写权限由云函数控制。

**代价:** 为了实时性引入一个新集合、一套安全规则、以及一份永久的权限心智负担 ——
以后每次改 `messages` 的结构,都要回头确认安全规则还对不对。

### 方案 B:轮询(V1 采用)

进入群聊页时每 3 到 5 秒拉一次增量(`createdAt > lastSeen`),离开页面立即停止。
**全程走云函数,权限模型完全不变。**

---

## 3. 为什么 V1 选 B

| | 方案 A(watch) | **方案 B(轮询)** |
|---|---|---|
| 延迟 | 即时 | 3 到 5 秒 |
| 权限模型 | **需新增安全规则 + eventMembers 集合** | **不变,沿用云函数统一出口** |
| 新增概念 | 安全规则、成员凭据、连接生命周期 | 无 |
| 连接数配额 | 受 watch 并发上限约束 | 不涉及 |
| 与类目申报的匹配度 | 更像 IM | 更像行前沟通工具 |

**决定性理由:** 在「活动前几小时、10 个人、发几条到场信息」这个场景里,**3 秒延迟察觉不到**,
而 watch 带来的复杂度是**永久**的。

**升级路径清楚:** 消息读写接口不变,把前端轮询换成 watch 即可,后端只需补 `eventMembers` 与安全规则。
等真出现「群里聊得很热」的信号再升级 —— 目前没有任何证据表明会。

## 4. 实现要点(已落地)

### 云函数 `chat`
| action | 说明 |
|---|---|
| `list` | 拉增量:`{ eventId, since }`,返回 `createdAt > since` 的消息,按时间升序,单次上限 50 条 |
| `send` | 发消息:**必须先过 `security.msgSecCheck`**(T28);校验调用者是该局 `confirmed` 成员;校验 `chatArchivedAt` 为空 |

### 前端
- 进页面拉全量(最近 100 条),之后每 4 秒拉增量;
- `onHide` / `onUnload` 立即清除定时器 —— 后台还在轮询是纯粹的浪费;
- 顶部常驻「本群将在活动结束 48 小时后关闭」(`03` §7 的类目缓解措施);
- 归档后输入框禁用,历史可见。

### 归档
已在 `cloudfunctions/formation` 实现:`done` 满 48 小时 → `archived`,写入 `chatArchivedAt`。
`chat.send` 检查该字段即可,不需要额外的定时任务。

### 退避
连续 5 次拉到空结果时,轮询间隔从 4 秒退到 10 秒;有新消息则立即恢复 4 秒。
减少无谓调用,同时保证有人在聊时的响应速度。

## 5. 落地后的补充说明

### 内容安全的降级策略(与发局文案不同)

`chat.send` 必须过 `security.msgSecCheck`。三档处理:

| suggest | 处理 |
|---|---|
| `pass` | 正常入库 |
| `review` | **入库但标记**,进 `reviewQueue` —— 直接拒会误伤地名、外语、口语 |
| `risky` | 拒绝,提示用户 |

**⚠️ 接口调用失败时放行并标记 `unchecked`,不拦截。**
理由:内容安全接口超时或配额耗尽时,拦截意味着活动当天所有人发不出「我到了」。
而这是最多 10 人、且都已通过报名的行前沟通群,传播面极小,全部留痕可事后复核。

**同一套判读逻辑在发局文案上取舍不同** —— 发局文案会出现在公开列表页,传播面大得多,
因此 `events.create` 对 `risky` 直接拒绝。取舍随传播面变化,这一点写在 `common/moderation.js` 的注释里。

### 轮询的实际行为

| 情况 | 间隔 |
|---|---|
| 有人在聊 | 4 秒 |
| 连续 5 次拉到空 | 退避到 10 秒 |
| 冷场中有人说话 | **立刻回到 4 秒** |
| 页面不可见 | 停止 |
| 自己发完消息 | 立刻拉一次,不等周期 |

退避逻辑是 `common/chat.js` 的 `nextPoll()` 纯函数,有单元测试锁定 ——
尤其是「冷场退避不能拖慢正在进行的对话」这一条。
