# A 组:成团规则

## D01 「成团率」的精确口径

**阻塞什么:** 北极星指标,埋点与看板都依赖它。口径不定,做出来的数字无法用于决策。

**默认值:**
- **分母** = 审核通过并公开过的局(不含被拒、不含草稿、不含从未公开的)
- **分子** = 在成团判定时点,报名数 ≥ 该场景最低成团人数的局
- **局主在判定前自行取消的局** → 计入分母,算作未成团(否则可以靠取消来刷高)
- **必须按 `is_official` 分组统计**,官方局与非官方局分开看

**为什么:** 分母把「被拒的局」排除,是因为那是审核在起作用,不是产品没跑通;把「局主取消」算作未成团,是因为不这么算就有刷分口子。分组统计的理由见 D12。

## D02 每个场景的「最低成团人数」

**阻塞什么:** 发局表单里**根本没有这个字段**,但成团判定要用它。这是 PRD 的一个实打实的空洞。

**默认值(且由系统按场景固定,不让局主填):**

| 场景 | 最低成团人数 | 说明 |
|---|---|---|
| 咖啡局 | **2** | 局主 + 1 人 |
| 展览/市集局 | **3** | 局主 + 2 人 |
| 晚间酒馆局 | **4** | 局主 + 3 人 |

**⚠️ 必须明确的一点:上述人数「含局主」。** PRD 没说,而含不含差一倍。默认含。

**为什么不让局主填:** 局主为了让自己的局能成,会一律填最小值,这个字段就失去意义了。
**为什么酒馆是 4:** PRD §5 说除咖啡外默认三人以上,酒馆是风险最高的场景,4 人比 3 人更难出现两两配对的氛围。

## D04 成团判定的时间点

**阻塞什么:** 「未达标自动解散」——什么时候判?这是成团引擎(T14)的核心参数。

**默认值:活动开始前 12 小时**,且**做成配置项而非写死**。

**为什么是 12 小时:** 周六下午 3 点的局,周五晚 9 点前出结果,用户还来得及安排别的事。这是「不让人干等」的最低要求。

**为什么要做成配置项:** 冷启动期人少,12 小时可能截掉了本来会在当天早上报名的人。如果实测成团率不达标,把它调到 6 小时是最便宜的补救手段——但前提是别写死在代码里。

| 备选 | 影响 |
|---|---|
| 24 小时 | 更保险,但报名窗口短一整天,冷启动期会显著拉低成团率 |
| 6 小时 | 成团率高,但用户当天才知道黄了,体验差 |

## D05 成团后是否锁定报名

**阻塞什么:** 状态机 `formed` 状态的行为定义。

**默认值:不锁定。** 成团后继续开放报名,直到 `capacity_max` 或活动开始前 2 小时(以先到者为准)。新报名者直接进 `confirmed`。

**为什么改了原方案:** 我在 `02` §4 里原本写的是「成团即锁定」,理由是给参与者确定性。但冷启动期最大的风险是密度不够(PRD §9 排第一的风险),锁定会白白浪费掉已经成团之后的报名意愿。
**确定性怎么保证:** 已确认的人在成团时就收到了通知,时间地点不会变,只是人可能更多一点——这对体验是加分不是减分。

**取消规则:** 进入 `formed` 之后取消,记 1 次爽约(见 D10)。

# B 组:审核与安全

## D06 人工审核的 SLA 与超时兜底

**阻塞什么:** 审核队列(T13)的设计。没有 SLA,周五晚上发的局周六才审,这个局就死了。

**默认值:**
- 承诺 **2 小时内**审完(所以后台必须手机可用,见 T13 验收标准)
- 超过 **6 小时**未审 → **自动放行**,并标记为「已通过·待复核」高亮显示
- 局主端全程可见审核状态

**为什么敢自动放行:** 冷启动期发局的基本都是熟人(PRD §6 第一、二阶段),内容风险远低于「局卡在队列里死掉」的密度风险。自动放行的局会高亮,Victor 事后可随时下架。
**什么时候要收紧:** 出现第一个完全陌生的局主时(PRD §6 第三阶段),把自动放行改成「自动进入限流展示」而非完全放行。

## D07 性别配比规则(PRD §5 算法层第一条的落地)

**阻塞什么:** 报名校验逻辑(T16)。原规则在小人数下**数学上锁死**:2 人咖啡局只要两个同性就是 100% 超标直接封禁;3 人局 2 男 1 女正好 66.7% 卡线,第三个位置只能给女性——界面上无法向用户解释「你为什么不能报名」。

**默认值:**

| 规则 | 咖啡 / 展览局 | 晚间酒馆局 |
|---|---|---|
| 生效阈值 | 报名数 **≥ 4** 才启用 | **全程启用**(n≥2) |
| 拦截方式 | **软拦截**:超配性别的新报名转候补,文案「该性别名额暂满,已加入候补,有人取消会第一时间通知你」 | **硬规则**:成团判定时若配比不满足,该局不成团 |
| 比例 | 单一性别 ≤ 2/3 | 单一性别 ≤ 2/3 |

**为什么软拦截:** 直接拒绝一个想参加活动的人,是产品能做的最伤人的事之一。转候补既守住了规则,又保留了希望,还能在有人取消时自动递补(这本身是提高成团率的机制)。
**为什么酒馆例外:** PRD §3 明确说酒馆「风险最高,需要更严的审核与性别配比规则」,这里就是那个「更严」的落点。

## D08 性别信息的采集方式

**阻塞什么:** D07 和 PRD §5 整个算法层都依赖性别字段,但 PRD §4.1 的报名流程**完全没有采集它**。

**默认值:**
- **首次报名时必填**,与昵称同屏(见 `03` §4 的报名流)
- 三个选项:**男 / 女 / 不便透露**
- **不做核验**(V1 无实名能力),用户协议写明「自述性别不代表平台核验」
- 「不便透露」计入总人数,但**不参与 2/3 的分子计算**

**为什么给「不便透露」:** 强制二选一会劝退一部分人,而且在一个明确说「不做交友」的产品里,强制填性别本身就有点自相矛盾。给出口更符合调性。
**边界情况:** 如果某场局「不便透露」超过一半,配比规则实际失效。早期量小,可接受。

## D09 地点数据的来源

**阻塞什么:** T03、T11(发局表单)的实现方式,以及审核成本。

**默认值:白名单 POI 库。**
- Victor 后台预录 **30 到 50 家**曼谷咖啡馆 / 展馆 / 酒吧
- **局主只能从列表中选,不能自由输入地址**
- V1.5 开放「申请新增场地」入口(局主提交 → Victor 审核后入库)

**为什么(四个理由叠加):**
1. 假地址与钓鱼风险归零;
2. 审核成本大幅下降(地点不用看了,只看时间和文案);
3. 能统计**场地维度的成团率**,直接支撑 PRD §3「曼谷咖啡馆密度极高,永远有新地方」这句话变成产品能力;
4. **不依赖腾讯位置服务对曼谷的 POI 覆盖质量**——那个还没实测,白名单方案让它变成不重要的问题。

## D10 取消与爽约的定义和处罚

**阻塞什么:** PRD §5 说「评价只评靠谱度(是否准时、是否放鸽子)」,但什么算放鸽子、放几次有什么后果,全都没定义。

**默认值:**

| 行为 | 判定 |
|---|---|
| `open` 状态下取消 | **不算爽约**(鼓励尽早取消,把位置让出来) |
| `formed` 之后取消 | **1 次爽约** |
| 未取消且未到场(局主活动后一键标记) | **1 次爽约** + `no_show` 计数 |

| 累计次数 | 后果 |
|---|---|
| 2 次 | 限制报名 **14 天** |
| 3 次 | 进人工复核,由 Victor 决定是否封禁 |

**可见性:** 爽约记录**只对局主可见**(报名者列表中显示靠谱度分),**不向其他参与者公开**——公开会制造评判感,与产品调性冲突。

# C 组:指标与商业

## D11 是否收报名保证金(PRD §10-1)

**阻塞什么:** 这一条直接决定要不要接支付。接支付 = 收款 + 退款 + 对账 + 客服,至少多 2 到 3 周工期。

**默认值:V1 不收。**

**为什么:**
1. 与定位冲突 —— PRD §3 说咖啡局「**失败成本几乎为零**」,收保证金等于亲手把成本加回去;
2. 咖啡局人均才 ฿150-300,保证金要么太小没约束力,要么太大劝退;
3. 冷启动期最大的风险是**没人来**,不是**来了不靠谱**。先解决前者;
4. 已有 D10 的爽约记录 + 局主可见靠谱度作为替代约束。

> 注:企业主体已解锁微信支付,所以这是**纯产品决策,不是技术限制**。想收随时能做。

**什么时候重新考虑:** 实测爽约率 **> 25% 且持续 4 周**。低于这个数就不值得为它付出转化率代价。

## D12 北极星指标是否拆成双指标

**阻塞什么:** 看板设计,以及「产品到底跑没跑通」的判断标准。

**问题:** PRD 定的「成团率 > 60%」在冷启动期是**被保送的**——Victor 自己发局(§6 第一阶段)+ Victor 亲自补位凑人(§9 缓解措施)+ 咖啡局只要 2 人成团(D02),三条叠加,成团率会天然接近 100%,指标完全失真。

**默认值:拆成两个。**

| 指标 | 定义 | 目标 |
|---|---|---|
| **保健指标** | 整体成团率(含官方局) | > 60% —— 确保用户体验不崩 |
| **真北极星** | **非官方局成团率** = `is_official=false` 且 Victor 未作为报名者补位 | **8 周内 > 40%** |

**为什么真北极星只要 40%:** 因为它衡量的是「完全靠产品本身能不能凑齐人」,这个数在冷启动期到 40% 已经是很强的信号了。它和 PRD §6 第三阶段「陌生用户主动开局并成团才算跑通」是同一件事的量化版本。

**实现要求:** `events` 需要 `is_official` 字段,`signups` 需要「Victor 补位」标记。

## D14 局主是否给激励、给什么(PRD §10-3)

**默认值:第一阶段只给「免单」,不给现金,不做抽成。**

## D15 品牌名与调性(PRD §10-4)

**这一项不阻塞开发**,代码里用占位符,改名成本极低。但类目申报和小程序注册要用,所以别拖太久。

**命名原则(比候选名更重要):**
1. **不能有交友暗示** —— 排除「约、伴、遇、缘、恋、友」这类字;
2. **最好是动词或场景,不是身份** —— 「出门」是动作,「搭子」是身份,身份词更容易被理解成「找一个人」;
3. **能在微信群里被自然地说出来** —— 「我在 XX 上开了个局」要顺口;
4. 小程序名唯一,注册前先查重。

**候选方向(供参考,不必采纳):**

| 方向 | 例子 | 感觉 |
|---|---|---|
| 动作型 | 出门吧 · 走一个 · 出来晒 | 轻,有行动感,零交友暗示 |
| 时间场景型 | 周末计划 · 下午三点 · 这周六 | 具体,像日程工具而非社交产品 |
| 中性容器型 | 有空 · 空档 · 开局 | 抽象,可延展,但需要解释 |

**我的倾向:** 「**周末计划**」这类时间场景型最安全——它听起来像一个日程工具,恰好完美掩护了社交属性,也最容易通过非社交类目的申报。
