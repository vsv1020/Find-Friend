# 数据模型与集合设计(微信云开发)

> 对应 `02-任务拆解与落地方案.md` §3 的关系模型改写版。
> 规则常量见 [`config/rules.js`](../config/rules.js);状态机见 [`02` §4](02-任务拆解与落地方案.md) 与 `cloudfunctions/common/state-machine.js`。

---

## 0. 一条不可动摇的原则

PRD §5「防滑向约会」的结构设计不能靠前端不显示来保证,必须落到数据层。本设计的三条硬约束:

1. **不存在按人检索的接口。** `users` 集合对小程序端**完全不可读**,所有访问经云函数;云函数中也没有、且不得新增任何「列出用户」「搜索用户」的 action。
2. **局详情只返回计数,不返回身份。** `events` 的对外投影由 `cloudfunctions/events/index.js` 的 `publicEvent()` 白名单显式控制——将来加字段不会误泄露。
3. **群聊按局隔离且定时归档。** `messages` 仅同局 `confirmed` 成员可读写,`chatArchivedAt` 后转只读。

---

## 1. 集合一览

| 集合 | 用途 | 小程序端权限 |
|---|---|---|
| `users` | 用户 | **不可读不可写**(仅云函数) |
| `events` | 局 | **不可读不可写**(仅云函数,经白名单投影) |
| `signups` | 报名 | **不可读不可写**(仅云函数) |
| `messages` | 局内「行前沟通」(V1.0) | 仅云函数 |
| `reliabilityMarks` | 靠谱度评价 | 仅云函数 |
| `notifications` | 通知队列 | 仅云函数 |
| `reviewQueue` | 人工复核队列(内容安全命中、重复爬约) | 仅云函数 |
| `eventStatusLog` | 状态流转日志 | 仅云函数 |
| `analyticsEvents` | 埋点 | 仅云函数 |
| `settings` | 全局配置(D06 自动审核开关等) | 仅云函数 |

> 云开发的「数据权限」全部设为**仅管理端可读写**,前端一律走云函数。这是上面三条硬约束的实现方式。

## 2. users

```js
{
  _id, openid,                 // openid 为登录态锚点,云函数自动注入
  phone,                       // getPhoneNumber 采集,账号唯一性锚点(多为 +86)
                               // ⚠️ 不作通知通道 —— 见 docs/03 §4
  notifyPhone,                 // 可选的泰国本地号,V1.0 启用短信兜底时使用
  nickname, gender,            // D08 首次报名必填;gender ∈ male|female|other
  avatarUrl,
  isHost,                      // D14「给权限不给钱」:免审发局 + 优先展示 + 专属标识
  isAdmin,
  reliability,                 // 靠谱度分,默认 100
  noShowCount,                 // D10 累计爬约次数
  status,                      // active | restricted | banned
  restrictedUntil,             // D10 限制报名到期时间
  createdAt,
}
```
**索引:** `openid`(唯一)、`phone`(唯一,允许 null)

> ⚠️ **合规**:`gender` 在 V1 采集但不参与自动配比(D07 未启用)。
> 收集用途不明的个人信息在 PDPA 下属合规瑕疵,**隐私政策必须写明用途**(活动氛围平衡与安全审核)。见 `03` §8。

## 3. events

```js
{
  _id, hostId,
  sceneType,                   // coffee | art | bar
  venue: { name, address, lat, lng },   // D09 自由输入,但必须保存坐标
  startAt, durationMin,
  capacityMin,                 // D02 系统按场景固定,不接受局主传入
  capacityMax,                 // D03 局主可在 [min, hardMax] 内调整
  priceEstTHB, description,
  status,                      // 见状态机
  isOfficial,                  // D12 官方局标记
  adminFilledIn,               // D12 管理员补位标记 —— 补位过的局不算「自然局」
  confirmedCount,              // 冗余计数,避免每次详情页都聚合 signups
  genderCounts: { male, female, other },  // 冗余,供 D07 在 V2 启用时使用
  publishedAt,                 // D01 成团率分母的判定依据:仅真正公开过的局才有值
  formedAt, endedAt, cancelledAt, chatArchivedAt,
  rallyNoticeSentAt,           // D04 催报名去重标记
  reviewedBy, reviewedAt, reviewNote,
  createdAt,
}
```
**索引:** `status + startAt`(列表查询)、`publishedAt`(指标)、`hostId`

**为什么冗余 `confirmedCount` / `genderCounts`:** 文档型数据库没有 JOIN,详情页与列表页若每次聚合 `signups` 会很慢。计数在报名/取消的同一次操作中用 `_.inc()` 原子更新。

### 坐标的用途(D09 的补偿设计)
自由输入放弃了白名单,但**保存 `lat`/`lng` 使场地热度仍可统计** —— 按 geohash 6 位(约 ±0.6km)聚合,同一家店的多次选点会被聚到一起。见 `VENUE.heatmapGeohashPrecision`。

## 4. signups

```js
{
  _id, eventId, userId,
  status,                      // applied | waitlist | confirmed | cancelled | attended | no_show
  gender,                      // 报名时快照,避免用户改资料后历史统计漂移
  createdAt, cancelledAt,
}
```
**索引:** `eventId + userId`(唯一,防重复报名)、`eventId + status`(候补递补按 createdAt 排序)、`userId + createdAt`

## 5. messages

```js
{
  _id, eventId, userId, content, createdAt,
  moderation,   // 仅当内容安全判为 review 或调用失败时存在:
                // { suggest: 'review'|'unchecked', label, error }
}
```

**这里没有「群」这张表。** 所谓群 = 同一个 `eventId` 下所有消息的集合,是查询的结果而非需要创建的对象。
因此「成团后自动建群」在实现上等于「把已存在的空间对该局成员放出来」,零成本。

**读写条件(云函数强制,见 `common/chat.js`):**
- 读:局处于 `formed`/`done`/`archived`,且调用者是 `confirmed`/`attended` 的报名者。**候补进不去**。
- 写:上述条件 + `chatArchivedAt` 为空。

归档后转只读 —— 这是 PRD §4.1「不沉淀私聊关系链」的实现点,不是可选优化。
归档由 `cloudfunctions/formation` 在活动结束满 48 小时后写入 `chatArchivedAt`,`chat` 只读该字段。

**为什么不用 `db.watch`:** 见 [`06-群聊技术方案.md`](06-群聊技术方案.md) §2 —— watch 走数据库权限而非云函数,
与本文 §0 的三条硬约束直接冲突。

**索引:** `eventId + createdAt`(轮询拉增量靠它)

## 6. reliabilityMarks

```js
{ _id, eventId, raterId, rateeId, mark, createdAt }
// mark ∈ on_time | late | no_show —— 仅此三个枚举,不可扩展
```
**为什么枚举不可扩展:** PRD §5 结构层第四条「只评靠谱度,不评外貌、不评好感」。一旦允许自由文本或增加维度,产品性质就变了。这个约束写在代码里(`RELIABILITY_MARK`),不靠人记住。

## 7. notifications

```js
{
  _id, userId, eventId, templateKey, payload,
  channel,                     // wx_subscribe(主) | sms(V1.0 兜底) | in_app
  status,                      // pending | sent | failed
  dedupeKey,                   // `${userId}:${eventId}:${templateKey}` —— 定时任务幂等的关键
  sentAt, error, createdAt,
}
```
**索引:** `dedupeKey`(唯一) — 定时任务必然重复执行,靠唯一索引兜住重复发送。

**模板:** `event_formed` · `event_cancelled_low` · `event_rally` · `waitlist_promoted` · `review_invite`

## 8. eventStatusLog / analyticsEvents / settings

```js
// eventStatusLog:每次状态流转都写,排障时能还原完整时间线
{ _id, eventId, from, status, reason, changedAt }

// settings(单文档 _id='global')

```

## 10. 与 `02` §3 关系模型的差异

| 项 | `02` 原设计(Postgres) | 本设计(云开发) |
|---|---|---|
| 主键 | `phone` | `openid`,`phone` 降为唯一索引 |
| 外键约束 | 数据库强制 | 手动维护 + 云函数校验 |
| 计数 | 实时聚合 | 冗余字段 + 原子 `inc` |
| 访问控制 | Row Level Security | **云函数统一出口 + 集合权限设为仅管理端** |
| 场地 | `venues` 白名单表 | D09 改自由输入,`venue` 内嵌于 `events`;推荐场地另存 |

**护城河没有变** —— 换了实现手段,「禁止按人检索」这条约束依然是硬的。
